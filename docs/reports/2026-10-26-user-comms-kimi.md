VERDICT: Email is a good channel but the wrong first fix — the cheapest, highest-yield moves are (1) stop letting USDC-empty wallets link silently (server-side, deploys today), (2) make the server surface everything it already logs so any single app open or background tick catches the user up, and (3) add Expo server push (the Seeker ships Google Play); build optional double-opt-in email after that as the durable channel for pauses, Terms changes and security notices.

## B. Is email the best fix for the no-USDC pause?

**What each option actually buys, per unit of founder effort:**

1. **Prevention at link time (S, API-only, deploys instantly).** The pause is partly manufactured at onboarding (section D). A server-side USDC balance check in `link/confirm` that warns — and for the phone wallet already has a remedy (TopUp, `repo/app/src/lib/topup.ts:25-35`) — stops new wallooms/coin35s before they exist. Highest effect per effort; do first.
2. **Server-side catch-up surfacing (S, API-only).** Today a notice only fires if Android runs the background task *twice* bracketing the event (`repo/app/src/lib/notices.ts:26-27`). If the server marked events unacknowledged and `/api/me` carried them, one single run of anything (app open, one background tick) would deliver the truth. Doesn't reach a user who *never* opens the app, but fixes delivery for everyone who opens it even occasionally — with zero app release.
3. **Widget fix (S, needs app release).** The widget is always visible and already shows "Paused" (`repo/app/src/lib/widget-state.ts:23`), but Garden2 says "Open Sprouts to turn them on" (`repo/app/src/lib/widget-state.ts:59`) — wrong for no-USDC, where Home deliberately hides the switch because the run auto-resumes (`repo/app/src/app/(tabs)/home.tsx:281`). It should say "add USDC" with the amount. Cheap, moderate effect (users glance at their home screen far more often than they open the app), but the widget never fetches itself (`repo/app/src/garden/Widget.tsx:33`), so it still depends on the background task having run once — pair it with #2.
4. **Server push via Expo Push (M, needs app release + dApp Store review).** `expo-notifications` is already a dependency (`repo/app/package.json:54`); the only missing pieces are token registration and a sender — `repo/app/src/lib/notify.ts:12` states "Local, no push service, no FCM." The charge's open question is settled: **the Seeker ships the Google Play Store** ([Blockworks review](https://blockworks.com/news/seeker-review-solana-mobile)), so FCM works. Push reaches users who don't open the app, on-device, with an action. Costs one app release — and the screenshots in `screens/3ea33d8c-image.png` show this team has already had a dApp Store submission rejected once (version progression), so releases are real friction.
5. **Email (M, no app release strictly required if collected on the web link page, realistically collected in-app).** The only channel that survives app abandonment and uninstall, and the right channel for Terms changes and security notices regardless of the pause problem. But for the *pause problem specifically* its reach is gated by opt-in uptake among a privacy-minded audience — the users most likely to go silent are plausibly the least likely to hand over an email. It also carries fixed costs push doesn't: double opt-in flow, DB column + deletion path, SPF/DKIM/DMARC warm-up on a fresh domain, template copy, Terms/privacy edits.
6. **Auto top-up from SOL (option 4) — defer.** It needs a wSOL approval, which widens the approval surface the whole product promises to keep minimal ("Plants up to $5 of USDC a day", `repo/app/src/lib/safety-copy.ts:6`). Solving a communication problem by expanding trust assumptions is backwards.
7. **On-chain/wallet-native — skip.** A memo costs lamports, looks like spam, and no major wallet surfaces memos as notifications. Dialect's wallet-notification reach on Seeker is unproven and adds a dependency. X/Telegram is fine for founder-level incident comms, not per-user events.

**Ranking by expected effect on the paused-user problem per unit of effort:** 1 > 2 > 3 > 4 > 5 > 6 > 7. **Build the prevention and catch-up fixes this week (API-only), push in the next app release, email after push** — and when email ships, reuse the pause/resume copy the Acorns mail gets right (`screens/IMG_2229.PNG`): state the cause, state that it resumes on its own, state the one action.

## C. Risks of collecting email from this audience

- **Identity linkage / doxxing.** These users *trade* with the linked wallets. An email↔wallet row ties a pseudonymous on-chain history to a real identity; a single breached table is a target list ("this person has a funded Solana wallet") plus their trading behavior. Minimise: store only `email + user pubkey + opt-in state` — no name, no engagement data; offer delete-email (which also forces building the account-deletion endpoint that doesn't exist today); never log email bodies.
- **Consent/legal.** Double opt-in covers consent; keep emails strictly transactional (pause, resume, terms, security) so they stay out of marketing-law territory in most jurisdictions. Update the Terms (`repo/app/src/lib/terms-text.ts`) and the privacy section the privacy page redirects to (`repo/api/src/app/privacy/page.tsx` → `/terms#data-we-keep`) before collecting anything, and bump `TERMS_VERSION` (`repo/api/src/lib/terms.ts:2`) — which, per section A, currently notifies nobody, so the first email announcing email collection is itself the test case.
- **Deliverability.** A brand-new sending domain (sprouts.money) with ~14 sign-ups a week has near-zero volume — that means no spam-trap risk but also no sender reputation, so early mails can land in spam exactly when they matter. Minimise: SPF + DKIM + DMARC from day one, plain-text-first templates, one consistent From address, no tracking pixels or open/click analytics (both for deliverability hygiene and because tracking pixels would be hypocritical for this product).
- **Phishing surface.** Any "your wallet needs attention" email trains users to be phished. Mitigate in copy: every email says Sprouts will never ask for a signature, seed, or approval via email, and calls to action point at "open Sprouts" rather than deep links that trigger signing.
- **Channel quality.** Privacy-minded users will give throwaway or relay addresses; expect a meaningful share of dead inboxes and don't treat email as guaranteed delivery — which is exactly why it complements rather than replaces push.

## D. Root cause check

**It is both, and the onboarding half is the fixable half.** The link flow *does* check USDC — but only for the phone's own Seed Vault wallet, only as an advisory note, and it "never blocks linking" (`repo/app/src/lib/safety-copy.ts:22`; note builder at `:24-31`; wired at `repo/app/src/app/connect.tsx:61-68`, where a failed read silently yields no note). The **"another wallet" code path — the path a user takes to link the wallet they actually trade with — performs no balance read at all** (`repo/app/src/lib/safety-copy.ts:16`, "Its balance is not read here"), offering only the static line "Each pays round-ups from its own USDC" (`:17`). walloom and coin35 trade SOL and other tokens, i.e. they are precisely the another-wallet case: they linked wallets that were never going to work, and nothing server-side checked either (`repo/api/src/app/api/link/confirm/route.ts` books the webhook and writes `wallet_linked`; no balance gate). The connect headline — "Every swap rounds up. Sprouts plants the change once a day." (`repo/app/src/app/connect.tsx:111`) — never mentions USDC; the pause consequence exists only in the Terms and in Home's *next-planting* copy ("planted within the hour", `repo/app/src/lib/next-planting.ts:57-58`), which sets a same-day expectation right before the wallet pauses.

The communication half then compounds it: Home surfaces the pause well (top of screen, attention dot, exact resume amount, one-tap TopUp — `repo/app/src/app/(tabs)/home.tsx:282-295`, copy at `repo/app/src/lib/me-state.ts:94`), but only if you open the app; the off-app path is a local notification that fires only if Android schedules the background task twice around the event (`repo/app/src/lib/notices.ts:26-27`, `repo/app/src/lib/background.ts:14`). A paused user who doesn't open Sprouts can stay paused indefinitely — there is no escalation or "paused N days" nudge anywhere in `plant-run.ts`.

**What stops new users entering this state:** a server-side USDC balance check in `link/confirm` for *every* wallet path (zero USDC → strong warning + suggested top-up before the first planting, rather than silent success); keeping the existing phone-wallet note but making it impossible to miss; and a first-planting-expectation line in connect copy that names USDC. All API/copy changes — no dApp Store release required for the server half.
